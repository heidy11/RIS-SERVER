Sistema RIS + PACS · versión del 1 de octubre de 2026

Guía de instalación en servidor

Cómo montar el RIS (frontend y backend) en un servidor con Docker, conectarlo a un PACS, publicarlo con dominio y resolver los problemas que ya aparecieron en los servidores de producción.

1. Arquitectura

El sistema son dos repositorios y un PACS:

ParteRepositorioQué es
Backendheidy11/RIS-SERVERAPI (Node.js + MongoDB). Guarda los datos y manda cada cita a la worklist del PACS.
FrontendMED-RIS/RISEl sistema que usa el personal, en el navegador.
PACSDCM4CHEE (imagen oficial de Docker)Worklist DICOM e imágenes. Puede ser uno existente o el de laboratorio del repo (pacs-lab).

En el servidor de producción, cada parte corre en un contenedor Docker con un puerto propio, y el nginx del servidor (fuera de Docker) recibe el tráfico HTTPS de cada dominio y lo reparte al puerto que corresponde:

Internet ──HTTPS──▶ nginx del servidor (certificados certbot)
                       ├── ris.<cliente>.signa-engineering.com   ──▶ contenedor frontend (puerto propio)
                       └── dominio del backend                    ──▶ contenedor backend  (puerto propio)
contenedor backend ──REST──▶ PACS (DCM4CHEE)        contenedor backend ──▶ MongoDB

2. Requisitos

  • Servidor Linux con Docker y Docker Compose, y un usuario que pueda usar Docker (grupo docker).
  • Git.
  • Acceso root o sudo solo para: configurar nginx, emitir o renovar certificados y el firewall. Sin eso hay que pedírselo al administrador del servidor.
  • Un registro DNS del dominio apuntando a la IP del servidor (lo crea quien administra el DNS de signa-engineering.com).

3. Backend (RIS-SERVER)

Descargar y configurar

git clone https://github.com/heidy11/RIS-SERVER.git ris-server-<cliente>
cd ris-server-<cliente>
cp .env.example .env
nano .env

Variables a definir en el .env:

VariableQué poner
JWT_SECRETUna clave al azar, propia de esta instalación. Generarla con openssl rand -hex 32.
ADMIN_EMAIL / ADMIN_PASSWORDEl administrador inicial. Se crea la primera vez que arranca el backend. Nunca dejar los valores de ejemplo.
MWL_ENABLEDtrue para que las citas lleguen a la worklist.
MPPS_ENABLEDtrue para recibir el estado del estudio desde el equipo.
DCM4CHEE_BASE_URLDirección del PACS, por ejemplo http://localhost:8080/dcm4chee-arc.
DCM4CHEE_AETAE Title del archivo del PACS (ver sección 5).
DCM4CHEE_MWL_AETAE Title de la worklist del PACS (ver sección 5). No viene en el .env.example: agregar la línea si el PACS no usa WORKLIST.

Antes de levantar: puertos solo hacia adentro

El docker-compose.yml del repo publica MongoDB y el backend a toda la red. En un servidor con IP pública, editar los puertos para que solo los vea el propio servidor (nginx sigue llegando igual):

    ports:
      - "127.0.0.1:27017:27017"     # mongodb-server: antes "27017:27017"
    ...
    ports:
      - "127.0.0.1:5000:5000"       # backend-server: antes "5000:5000"

Si en el servidor ya hay otra instalación, cambiar también el container_name de los dos servicios y el puerto del lado izquierdo (por ejemplo 127.0.0.1:5003:5000): los nombres y puertos no pueden repetirse en todo el servidor.

Levantar y verificar

docker compose up -d --build
docker compose logs -f backend-server

En los logs tienen que aparecer MongoDB Conectado... y [MWL] Adapter activo. Salir de los logs con Ctrl+C (el backend sigue corriendo).

Si se cambia ADMIN_PASSWORD después del primer arranque, aplicarlo con docker compose exec backend-server node scripts/reset-admin.js: el backend no actualiza la contraseña solo.

4. Frontend (RIS)

git clone https://github.com/MED-RIS/RIS.git ris-<cliente>
cd ris-<cliente>
nano .env

En el .env, VITE_API_URL con la dirección pública del backend, por ejemplo VITE_API_URL=https://api.<cliente>.signa-engineering.com.

Importante: VITE_API_URL queda fijo dentro del frontend al compilarlo. Si se cambia después, hay que volver a compilar (docker compose up -d --build ris-prod).

En docker-compose.yml, servicio ris-prod: poner un container_name único en el servidor (por ejemplo ris-<cliente>-frontend-prod) y el puerto con el que lo va a buscar nginx (por ejemplo "127.0.0.1:6001:80"). Después:

docker compose up -d --build ris-prod
docker ps | grep ris-
Nunca usar el servicio ris-dev detrás de un dominio público. Es el servidor de desarrollo de Vite: permite leer archivos del servidor desde internet. ris-prod compila el sistema y lo sirve con nginx, sin ese riesgo.

5. Conectar con un PACS existente

Cada instalación de DCM4CHEE puede tener sus AE Titles con otro nombre. Hay que averiguarlos, no suponerlos. Desde el servidor:

curl -s http://localhost:8080/dcm4chee-arc/aets

Responde la lista de AE Titles (por ejemplo, en el PACS de producción de CNS el que sirve es NUBEMEDVIEWER; los que terminan en _ADMIN o _TRASH no se usan). Probar la worklist con el candidato:

curl -s -o /dev/null -w "%{http_code}\n" "http://localhost:8080/dcm4chee-arc/aets/NUBEMEDVIEWER/rs/mwlitems?limit=5"
RespuestaSignificado
200 o 204Ese AE sirve la worklist (204 = funciona pero todavía está vacía). Usarlo en DCM4CHEE_AET y DCM4CHEE_MWL_AET.
404Ese AE no sirve la worklist: probar otro de la lista.

Las versiones viejas de DCM4CHEE (por ejemplo la 5.12 de producción) piden un formato distinto para dar de alta pacientes; el backend actual ya lo detecta y se adapta solo.

6. Credenciales

  • Ningún usuario ni contraseña real va en el código ni en la documentación: se definen en el .env de cada instalación, distintas en cada una.
  • El administrador inicial sale de ADMIN_EMAIL y ADMIN_PASSWORD la primera vez que arranca el backend.
  • Si alguna instalación quedó con la contraseña de ejemplo que circuló en el repositorio, cambiarla: es pública.
  • Las credenciales de cada ambiente se comparten por un canal privado, nunca por el repositorio ni por chat abierto.

7. Publicar con dominio y HTTPS

Requiere root o sudo. Pasos:

  1. DNS: registro A del dominio apuntando a la IP del servidor. Verificar con nslookup <dominio>.
  2. nginx: un bloque server por dominio que reenvíe al puerto del contenedor.
  3. Certificado: sudo certbot --nginx -d <dominio>. Certbot configura el HTTPS y la redirección desde HTTP.

Ejemplo de bloque nginx para el frontend (/etc/nginx/sites-available/<dominio>):

server {
    server_name ris.<cliente>.signa-engineering.com;
    location / {
        proxy_pass http://127.0.0.1:6001;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
sudo ln -s /etc/nginx/sites-available/<dominio> /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d <dominio>

El backend se publica igual, con su propio dominio y su puerto.

8. Seguridad: qué no debe quedar abierto a internet

Docker publica los puertos en todas las interfaces y además se salta el firewall del sistema (ufw), así que la protección real es publicar en 127.0.0.1. Revisar con docker ps: en la columna PORTS, lo que diga 0.0.0.0: está abierto a internet.

ServicioPuertos típicos¿Abierto a internet?
Frontend y backend5000, 6001…No: solo nginx los usa. Publicar en 127.0.0.1.
MongoDB27017, 27018…Nunca. No pide contraseña: cualquiera podría leer o borrar pacientes.
PostgreSQL5432, 5433…Nunca. La del PACS viene con contraseña de fábrica.
Consola web y administración de DCM4CHEE8080, 8443, 9990No. El 9990 es la consola de administración de WildFly.
DICOM del PACS11112Solo si los equipos se conectan desde afuera; idealmente limitado a sus IPs.
Estado al 1 de octubre de 2026 en el servidor de Contabo: los puertos 27018 y 27019 (MongoDB), 5432 y 5433 (PostgreSQL) y 8080, 8443 y 9990 (DCM4CHEE) aceptan conexiones desde internet. Corregirlo publicando esos contenedores en 127.0.0.1.

Para corregir un contenedor ya creado, en su docker-compose.yml cambiar "27018:27017" por "127.0.0.1:27018:27017" (y lo mismo con cada puerto) y volver a levantarlo con docker compose up -d. Los datos se conservan porque viven en volúmenes. Si el contenedor se creó con docker run, hay que recrearlo con el mismo volumen y la nueva publicación de puertos.

9. Actualizar una instalación

# backend
cd ris-server-<cliente>
git pull
docker compose up -d --build

# frontend
cd ris-<cliente>
git pull
docker compose up -d --build ris-prod

Si git pull se queja de cambios locales (es normal: el .env y el docker-compose.yml suelen tener ajustes propios del servidor), revisar con git status y, si son solo esos ajustes, usar git pull --autostash: guarda los cambios, actualiza y los vuelve a aplicar.

11. Checklist antes de dar por terminada una instalación

  • El backend muestra MongoDB Conectado... y [MWL] Adapter activo.
  • El frontend corre como ris-prod, nunca ris-dev.
  • Login probado con el usuario del .env desde la dirección pública. Si falla con "Credenciales inválidas": reset-admin (sección 10).
  • .env con valores propios: ni JWT_SECRET ni contraseñas de ejemplo.
  • AE Titles del PACS verificados con /aets y con la prueba de /rs/mwlitems.
  • En docker ps, ninguna base de datos ni consola de administración en 0.0.0.0.
  • Certificado vigente: revisar la fecha de vencimiento.
  • Prueba de punta a punta: agendar una cita y verla en la worklist.
